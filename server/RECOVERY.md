# Подготовка резервирования и восстановления

Эти действия выполняются после выбора сервера. Сейчас ничего не развёрнуто и таймер не включён. Для подготовки кода регистрация в Timeweb не нужна.

## Перед запуском

- Один экземпляр приложения, постоянный том `/data`, HTTPS-прокси. Node.js 24.
- Отдельный каталог копий `/backup` и ключ `/run/secrets/mydom-backup.key`. Пользователь node в контейнере должен читать ключ и писать копии; каталог ключа не должен быть доступен другим пользователям. Права ключа 600, каталога копий 700.
- Создать ключ командой `node server/backup.mjs keygen /secure/mydom-backup.key` и сохранить дополнительный экземпляр в защищённом месте отдельно от сервера. Команда не выводит ключ и не перезаписывает существующий файл. Не добавлять ключ в git или Docker-образ.
- Подключить каталог копий в контейнер на запись, файл ключа только на чтение. В env-файле контейнера указать `BACKUP_DIRECTORY=/backup`, `BACKUP_KEY_FILE=/run/secrets/mydom-backup.key`; `DATABASE_PATH` уже задан образом.
- При миграции домена скачать пользовательскую копию в приложении на старом домене, импортировать на новом, затем явно сохранить на сервер. Вход сам по себе данные не загружает.

## Ежедневная копия

Ручной пробный запуск: `docker exec mydom node server/backup-job.mjs`. Успех означает: сделан согласованный снимок SQLite, проверены целостность и структура документов, зашифрованный файл опубликован под уникальным именем. Ошибка даёт ненулевой код завершения и не заменяет прежние копии.

После успешного пробного восстановления скопировать `ops/mydom-backup.service` и `ops/mydom-backup.timer` в `/etc/systemd/system/`, выполнить `systemctl daemon-reload` и `systemctl enable --now mydom-backup.timer`. Проверить `systemctl list-timers mydom-backup.timer` и `journalctl -u mydom-backup.service`. Шаблон предполагает имя контейнера `mydom` и Docker по пути `/usr/bin/docker`; время — полночь по часовому поясу сервера с задержкой до 5 минут. Это не push-уведомление пользователю приложения.

Копии на том же сервере не защищают от потери сервера. Отдельно настроить перенос зашифрованных файлов в независимое хранилище и оповещение об ошибках. Автоматическое удаление копий пока не включено: перед запуском определить срок хранения и контролировать свободное место. При ежедневном копировании возможна потеря изменений с последней успешной копии; частоту выбирать по допустимому интервалу потери.

## Проверка восстановления

1. В отдельном приватном каталоге выполнить `BACKUP_KEY_FILE=/secure/mydom-backup.key node server/backup.mjs restore /backup/selected.enc /recovery/new.sqlite`. Файл назначения и его WAL/SHM должны отсутствовать. Исходная рабочая база не меняется.
2. Запустить отдельный тестовый экземпляр на другом локальном порту, указав восстановленную базу в `DATABASE_PATH`. Не открывать его публично. Проверить вход тестового пользователя, его квартиры, начисления, показания, обращения и ревизию. Все прежние сеансы сброшены: нужен повторный вход.
3. Для реального переключения остановить основной контейнер, сохранить старый том для отката и подключить проверенную базу на новом томе. Никогда не подменять файл работающей SQLite и не смешивать восстановленный файл со старыми WAL/SHM.
4. Запустить приложение, проверить `/api/health`, вход и данные. После проверки снова включить резервирование. Повреждение копии, неверный ключ или неверная структура должны останавливать восстановление, а не вести к запуску пустой базы.

Пароли остаются хешами в базе. Сам файл работающей базы не шифруется этим инструментом: шифруются отдельные резервные копии. Доступ к хосту, шифрование диска, внешнее хранилище, контроль сбоев и восстановление забытого пароля — отдельные задачи перед публичным запуском.
